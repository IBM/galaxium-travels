# Compliance Documentation — Galaxium Travels

*Prepared for: Security reviewers and compliance stakeholders*
*Scope: `booking_system_backend/` · `booking_system_frontend/` · `booking_system_inventory_hold_service/`*
*Evidence basis: Direct source-code analysis. All findings are grounded in specific file and line references.*

> **Material limitation — Java Inventory Hold Service:**
> `booking_system_inventory_hold_service/src/` does not exist. The service is represented only by `pom.xml`. All sections that reference this service reflect the declared intent in the POM description and the declared dependency set. No domain model, controller, or data-handling code exists to analyse.

> **Material limitation — data destruction on restart:**
> `booking_system_backend/seed.py` is called unconditionally on every server startup (`server.py:110`) and deletes all rows in all three tables before inserting demo data. As a result, the system does not accumulate real user or booking data across restarts in its current state. All data classification, retention, and access-control findings below reflect the system's design, not merely its current runtime behaviour.

## 1. Data Classification

The following data elements are collected, stored, or transmitted by the system. Classification tiers used: **Restricted** (personal or sensitive data requiring specific handling obligations), **Internal** (operational data with no direct personal data element), **Public** (freely disclosed or non-sensitive).

| Data Element | Classification | Collected By | Stored In | Transmission Path | Retention Policy |
|---|---|---|---|---|---|
| User full name | **Restricted — Personal Data** | `POST /register` (`UserRegistration.name`); MCP `register_user` | `users.name` — SQLite `booking.db` | Plaintext in HTTP request body (REST) and as a URL query string parameter in `GET /user?name=` (`server.py:176`) | No retention policy defined. Data is destroyed on every server restart (`seed.py:9–11`). No deletion endpoint exists. |
| User email address | **Restricted — Personal Data** | `POST /register` (`UserRegistration.email: EmailStr`); MCP `register_user` | `users.email` — SQLite `booking.db`, UNIQUE constraint | Transmitted as plaintext URL query-string parameter in `GET /user?email=` (`server.py:176`, `api.ts:66–68`) and in HTTP request bodies | No retention policy defined. Destroyed on every server restart. No deletion endpoint exists. |
| User session (name + email + user\_id) | **Restricted — Personal Data** | Set in browser at sign-in (`useUser.tsx:26`) | Browser `localStorage` under key `galaxium_user` as unencrypted JSON string | Not transmitted to server after initial lookup; remains in client storage | No expiry mechanism. Persists until the user explicitly logs out or clears browser storage. |
| Booking record (user\_id, flight\_id, status, booking\_time) | **Internal — Operational** | `POST /book` (`BookingRequest`); MCP `book_flight` | `bookings` table — SQLite `booking.db` | Plaintext JSON in HTTP responses | No retention policy defined. Destroyed on every server restart. |
| Booking timestamp (`booking_time`) | **Internal — Operational** | Written at booking creation (`services/booking.py:49`) | `bookings.booking_time` — ISO 8601 string in SQLite | Included in `BookingOut` API responses | Destroyed on every server restart. |
| Flight schedule data (origin, destination, times, price, seats) | **Public — Operational** | Seeded at startup (`seed.py:30–43`); no external ingestion | `flights` table — SQLite `booking.db` | Returned by `GET /flights` to all callers without authentication | Destroyed and recreated on every server restart. |
| Error detail messages (may echo user-supplied name or email) | **Restricted — Derived Personal Data** | Generated by service layer on validation failure | Not stored; returned in `ErrorResponse.details` | Included in HTTP response bodies and MCP exception messages (`server.py:40`) | Not stored persistently. Present transiently in HTTP responses and server process output. |
| API request/response data | **Internal — Operational** | Uvicorn access log (default format) | Process stdout; not persisted to file in the default configuration | N/A | Not retained; no log rotation, log file, or log shipping is configured. |

**Notes on data minimisation:**
- The `GET /user` endpoint (`server.py:176`) accepts both `name` and `email` as URL query-string parameters. Email addresses transmitted in query strings appear in server access logs, browser history, referrer headers, and proxy logs.
- The `ErrorResponse.details` field in `services/booking.py:34` echoes the registered name of a user (`existing_user.name`) back to any caller who supplies the correct `user_id` but incorrect `name`. This constitutes indirect disclosure of personal data to unauthenticated callers.
- No data minimisation controls, pseudonymisation, or anonymisation are applied to any data element.

## 4. Audit Trail Coverage

### What is logged

| Event | Logging Mechanism | Log Format | Storage Location |
|---|---|---|---|
| Inbound HTTP requests | Uvicorn default access log (auto-generated) | `INFO: {client_addr} - "{method} {path} HTTP/{version}" {status_code}` | Process stdout only; not written to file, not shipped to any log aggregator |
| Server startup message | `print()` statement in `seed.py:59` | `"Database seeded with elaborate demo data!"` | Process stdout only |

### What is not logged

The following events produce no application-level log entry. This list is exhaustive based on source-code analysis — no `import logging`, `logger`, or structured logging call appears in any backend file.

| Event Category | Specific Events Not Logged |
|---|---|
| **Authentication events** | User sign-in attempts (successful and failed); user registration (successful and failed); `EMAIL_EXISTS` errors; `USER_NOT_FOUND` errors |
| **Authorisation events** | Any access attempt — no authorisation layer exists, so no access decisions are recorded |
| **Booking state changes** | Flight booked (`status="booked"` written to DB); booking cancelled (`status="cancelled"` written to DB); seat count decremented or incremented |
| **Data access** | `GET /bookings/{user_id}` queries; `GET /user` lookups; `GET /flights` queries |
| **Errors and exceptions** | `ErrorResponse` objects returned to callers; MCP tool exceptions raised; database errors |
| **MCP tool invocations** | Any invocation of any of the six MCP tools by any AI agent |
| **Schema initialisation and data seeding** | `init_db()` execution; `seed()` execution and data wipe |
| **Application startup and shutdown** | No startup or shutdown log entries beyond the seed print statement |

### Where audit records are stored

Uvicorn's default access log is written to process stdout. In the current Docker configuration, stdout is available via `docker logs` but is not persisted beyond the container's lifetime. No log shipping, centralised log management (ELK, Splunk, CloudWatch), log rotation, or tamper-evident log storage is configured. There is no audit log for the frontend — `console.error` calls in `Flights.tsx:52` and `MyBookings.tsx:43` write to browser DevTools only.

### Audit trail gap summary

The system produces no application-level audit records for any security-relevant event. The only observable signal is the Uvicorn HTTP access log, which records request method, path, and HTTP status code. Because all endpoints return HTTP 200 regardless of outcome (see `docs/audit/code-quality-summary.md`, finding CQ-03), even successful booking and error responses are indistinguishable in the access log.

**Applicability: High, if deployed to serve users in the EU or UK.**

The system collects and processes personal data as defined by GDPR Article 4(1): full name and email address are directly identifiable personal data. If the system processes data of individuals located in the EU or UK — regardless of where the operator is located — GDPR applies.

| GDPR Requirement | Current Implementation Status | Source Evidence |

### SOC 2 (Service Organization Control 2 — AICPA)

**Applicability: Applicable if the system is offered as a service to customers or if customers' data is processed on their behalf.**

SOC 2 evaluates against five Trust Services Criteria (TSC): Security, Availability, Processing Integrity, Confidentiality, and Privacy.

| TSC | Assessment |
|---|---|
| **Security (CC series)** | Significant gaps. No logical access controls, no authentication, no authorisation, no encryption at rest, no vulnerability management programme, no change management pipeline (no CI/CD), and no incident detection capability. |
| **Availability (A series)** | Not assessable. No uptime SLA, no health-check instrumentation beyond the `GET /` endpoint, no redundancy, and no failover is defined. `seats_available` can go negative under concurrent load, indicating correctness issues under availability scenarios. |
| **Processing Integrity (PI series)** | Not met. The race condition on `seats_available` (`services/booking.py:19,44`) means booking operations are not reliably atomic. The unconditional startup data wipe means processing state is not durable. |
| **Confidentiality (C series)** | Not met. No encryption at rest or in transit is implemented at the application layer. Personal data appears in URL query strings and error messages. |
| **Privacy (P series)** | Not met. Overlaps substantially with GDPR findings above. No privacy notice, consent, retention policy, or data subject rights mechanism exists. |

A SOC 2 Type II audit of the system in its current state would identify material findings across all five Trust Services Criteria.

### PCI DSS (Payment Card Industry Data Security Standard)

**Applicability: Conditional — applicable if the system processes, stores, or transmits payment card data.**

The system as implemented does **not** process, store, or transmit payment card data. The `price` field in the `Flight` model (`models.py:19`) is an integer representing a ticket price in an unspecified currency unit. No payment processing integration, card number field, CVV field, or payment gateway interaction exists anywhere in the codebase.

The `pom.xml` description for the Java service states the service is intended to support completion of "payment" (`pom.xml:27`), but no Java source code exists and no payment flow is implemented.

**Current PCI DSS scope assessment: Out of scope** for the current implementation, provided no payment card data is introduced.

**Future scope note:** If a payment processing integration is added — whether directly or via a third-party gateway — PCI DSS requirements would apply to the cardholder data environment. The current architecture lacks the foundational controls (network segmentation, access control, encryption, logging, vulnerability management) that would be prerequisites for any PCI DSS scope definition.
