1 — Angular → React mental model

Most of your Angular knowledge transfers directly. The table below maps the Angular concept you know to its React equivalent used in this repo.

Key mindset shift
In Angular, you configure the framework (modules, DI providers, decorators). In React, you compose — components are just functions that return JSX. There is no magic injection; everything is an explicit import or prop.

3 — Routing & pages

Routes are declared in App.tsx using react-router-dom. There are exactly four routes:

URLPage componentWhat the user sees
/ Home.tsx Hero, feature cards, destination grid
/flights Flights.tsx Flight list with search, filters, booking modal
/bookings MyBookings.tsx User's confirmed bookings + pending holds
/destinations/:slug DestinationDetail.tsx Planet info page, facts, hazards, live departures

Every page is wrapped by Layout.tsx, which injects the Starfield background, the fixed Header, and the global toast notification system (react-hot-toast).

// App.tsx — the router lives here, not in a module
function App() {
  return (
    <BrowserRouter>
      <UserProvider>      // ← provides user state to the whole app
        <Layout>          // ← header + footer + starfield + toasts
          <Routes>
            <Route path="/"                    element={<Home />} />
            <Route path="/flights"             element={<Flights />} />
            <Route path="/bookings"            element={<MyBookings />} />
            <Route path="/destinations/:slug"  element={<DestinationDetail />} />
          </Routes>
        </Layout>
      </UserProvider>
    </BrowserRouter>
  );
}
Angular equivalent
Think of this as your AppRoutingModule but without a separate file — routes are declared inline. UserProvider is equivalent to providing a singleton service at the root module level.

5 — State management

There is no Redux or Zustand. State is handled at two levels:

ScopeHowWhere
Global user identity React Context + useState, persisted to localStorage hooks/useUser.tsx
Page / component state useState — flights list, modal open/closed, loading flags Inside each page component
Pending holds localStorage keyed by user ID utils/holdStorage.ts

Using the user context

// Any component that needs the logged-in user:
import { useUser } from '../../hooks/useUserContext';

function MyComponent() {
  const { user, setUser, logout } = useUser();

  if (!user) return <p>Not logged in</p>;
  return <p>Welcome, {user.name}</p>;
}
Angular equivalent
useUser() is your singleton UserService injected via constructor DI. The difference: you call the hook at the top of the function body instead of injecting in a constructor.

6 — API layer (services/api.ts)

All HTTP calls go through a single axios instance. Think of it as a flat collection of async service methods — no class, no DI token needed.

⚠ Critical gotcha: HTTP 200 ≠ success
The Python backend proxies the Java hold service and catches errors, returning them as HTTP 200 with a JSON body containing { error: "…" }. Always check the response body, not the status code. Use the isErrorResponse() type guard from api.ts. 
// The axios instance base URL resolves to /api in production,
// or VITE_API_URL from .env in local dev
const api = axios.create({ baseURL: import.meta.env.VITE_API_URL || '/api' });

// Correct error checking:
const result = await createQuote(quoteData);
if (isErrorResponse(result)) {
  // handle error — result.error has the message
} else {
  // result is a Quote — safe to use result.quoteId etc.
}

9 — User booking flow, end-to-end

This is the most important flow in the app. Tracing it connects the frontend to both backend services.

1
Browse flights — Flights.tsx Calls getFlights(filters) on mount and on filter change. Displays FlightCard for each result. Retries up to 3× with backoff if the API is slow.
2
Authenticate — UserIdentification.tsx If no user in context, a modal prompts login or registration. On success, setUser() writes the user to React Context and localStorage.
3
Select seat class — BookingModal.tsx step 1 User picks Economy, Business, or Galaxium. Each class has a feature list and price shown from the Flight object.
4
Get a quote — BookingModal.tsx step 2 Calls createQuote() → Python proxy → Java inventory service. Returns a Quote with a confirmed price and quoteId.
5
Place a hold — BookingModal.tsx step 3 Calls createHold(quoteId). Java service reserves the seat for 15 minutes. Hold is saved to localStorage via storeHold(). A countdown timer is shown.
6
Confirm the hold — HoldCard.tsx on My Bookings Calls confirmHold(holdId) → Java service calls Python /internal/bookings/from-hold → booking record created in SQLite. The hold is removed from localStorage.
7
View booking — MyBookings.tsx Calls getUserBookings(userId). Confirmed bookings appear in the "Active Bookings" section as BookingCard components.

10 — Critical gotchas

1. HTTP 200 can still be an error
The backend wraps Java service errors as HTTP 200 with { error: "…" } in the body. Never trust the status code alone. Always use isErrorResponse(result) after any quote/hold API call.
2. User context is not persistent across tabs by default
UserProvider reads from localStorage on mount. If you open a new tab the state loads correctly, but in-memory state changes won't sync live between tabs. Not a bug — just be aware when testing.
3. Hold expiry is enforced by the Java service (15 minutes)
The frontend shows a countdown from reservedUntil, but the actual expiry is server-side. If the timer reaches zero, the confirm button is disabled — but it would be rejected server-side even if you bypassed the UI.
4. Destinations are static data, not API calls
src/data/destinations.ts is a hardcoded list. The destination detail page and the destination names on flight cards come from this file, not from a backend endpoint. Adding a destination means editing this file.
5. VITE_API_URL controls which backend you hit
In local dev, create booking_system_frontend/.env.local and set VITE_API_URL=http://localhost:8001. Without it, Vite's proxy or the bundled default /api prefix is used.

11 — Getting started

Install and run

# From the repo root:
cd booking_system_frontend
npm install
npm run dev          # Vite dev server on http://localhost:5173

Run the backend too (optional but useful)

# In a separate terminal, from the repo root:
cd booking_system_backend
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
SEED_DEMO_DATA=true .venv/bin/python server.py
# Backend listens on :8001. Frontend proxies /api → :8001 via Vite.

Lint

cd booking_system_frontend && npm run lint

Build for production

cd booking_system_frontend && npm run build
# Output in dist/ — never edit this directory

Key files to read first (recommended order)

  1. src/types/index.ts — understand the domain model
  2. src/App.tsx — understand routing and context setup
  3. src/services/api.ts — understand all backend endpoints
  4. src/pages/Flights.tsx — most complex page, covers filters + modal flow
  5. src/components/bookings/BookingModal.tsx — the core user journey
