Issue #43 — Refund Preview on Cancel

#43 Draft · Reviewed July 2026

Summary

Add a cancellation preview to the cancel modal in MyBookings.tsx so users see a refund / fee / travel-credit breakdown before confirming. The modal opens immediately with an inline spinner while the preview loads asynchronously — the backend exposes a new GET /bookings/{id}/cancellation-preview REST endpoint and matching MCP tool backed by a pure policy-calculation helper. price_paid accepts float and all amounts are returned rounded to 2 decimal places; the approved same-day policy is zero-payout across all three values.

Key Decisions

Decision Choice Rationale
Same-day cancellation payout 0 / 0 / 0 Intentional zero-payout for same-day cancellations. Policy is approved; no travel credit exception needed.
Cancel modal loading UX Open immediately + inline spinner Modal opens fast; preview loads in place via spinner. Better experience on slow connections than blocking open.
price_paid data type float → float (2 dp) Real pricing uses decimals (e.g. $249.99). Function accepts float and returns amounts rounded to 2 decimal places.

Cancellation Policy

Days to departure Refund Fee Travel credit
7+ days100%0%0%
3–6 days75%10%15%
1–2 days50%25%25%
Same-day (0)0%0%0%

Open Items

  • Departure-time parsing: departure_time stored in two formats ("YYYY-MM-DD HH:MM" and ISO 8601 "YYYY-MM-DDTHH:MM:SSZ"). Must try both or use fromisoformat fallback — a single strptime pattern will silently break on live data.
  • Negative days guard: Bookings for already-departed flights should be treated as same-day (0) — confirm this edge case is covered in unit tests.
  • Already-cancelled bookings: Service function must return a sensible preview (not an error) for cancelled bookings — treat departure as past → same-day policy.
  • Out of scope: Actual refund processing (payment is a stub), MCP tool via running server, and e2e Docker tests are explicitly excluded.
